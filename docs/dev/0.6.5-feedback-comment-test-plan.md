# 0.6.5 — Feedback comment attachments + edit: manual test plan

Covers the two changes in `vendor/llama_bot_rails`:
1. Image previews for comment attachments (before posting and after).
2. Editing a posted comment.

## What automated tests already cover

`spec/controllers/llama_bot_rails/feedback_comments_controller_spec.rb` — 10 examples, green:

| Behaviour | Covered |
|---|---|
| Author can edit their own comment body | ✅ |
| Another user cannot (body unchanged) | ✅ |
| Empty body rejected, flash alert shown | ✅ |
| Existing attachments survive a body edit | ✅ |
| New attachments append, don't replace | ✅ |
| `(edited)` marker off before / on after an edit | ✅ |
| `editable_by?` — author / other user / signed out / anonymous comment | ✅ |

**Not covered by tests — this is what the manual pass is for:** all the browser JS
(thumbnail preview, lightbox, edit-form toggle) and the rendered markup itself.

## Setup

- Log into the dev app (https://rails-llamapress-dev.llamapress.ai) as a normal user.
- Go to the feedback board → open any item, or submit one.
- Have ready: a PNG/JPG screenshot, a second image, a PDF, a short video.
- Keep the browser console open — a JS error breaks the preview silently.

---

## A. Preview before posting

| # | Step | Expect |
|---|---|---|
| A1 | In the comment box, click **Attach files** → pick a screenshot | A **thumbnail of the actual image** appears below the box (whole image, not cropped), filename underneath |
| A2 | Click that thumbnail | Lightbox opens with the full image |
| A3 | Attach 2 images at once | Two thumbnails, each with its own filename |
| A4 | Attach a PDF | File icon + filename (no thumbnail — expected) |
| A5 | Attach a video | Video frame thumbnail on a black tile |
| A6 | Pick a different file with the same picker | Preview **replaces** the old one, doesn't stack |
| A7 | Post the comment | Comment appears with the attachment |

**This is the original complaint:** at A1 you should be able to tell which screenshot
you grabbed without opening it from disk.

## B. Attachments on a posted comment

| # | Step | Expect |
|---|---|---|
| B1 | Look at a comment with an image | Thumbnail is large enough to recognise (~112px tall), full image, not a cropped strip |
| B2 | Hover the filename | Tooltip shows the full name |
| B3 | Click the thumbnail | **Lightbox** opens (not a new tab): full image, filename, Download button |
| B4 | Press Esc / click the backdrop / click ✕ | Lightbox closes |
| B5 | Click Download in the lightbox | File downloads with the right name |
| B6 | Click the download icon under the thumbnail | Same |
| B7 | Click the trash icon under the thumbnail | Confirm → attachment removed, comment stays |
| B8 | Comment with a video attachment | Click plays it in the video modal (unchanged behaviour) |
| B9 | Attachments on the **feedback itself** (top of page) | Also open in the lightbox now |
| B10 | Reply (indented) with an image | Thumbnail visible + clickable, filename shown |

## C. Editing a comment

| # | Step | Expect |
|---|---|---|
| C1 | Your own comment | **Pencil** button between Reply and Delete |
| C2 | Someone else's comment | **No pencil** (Delete may still show if you're a moderator) |
| C3 | Click the pencil | Body is replaced by a textarea pre-filled with the current text; cursor at the end |
| C4 | Change the text → **Save** | Page reloads, new text shown, `(edited)` next to the timestamp |
| C5 | Click the pencil → **Cancel** | Original text back, nothing saved |
| C6 | Edit → clear the box → Save | Red flash "Failed to update comment: Body can't be blank", original text intact |
| C7 | Edit a comment that has attachments → Save | **Attachments still there** (regression watch — this is the easiest thing to break) |
| C8 | Edit → **Add files** → pick an image → Save | New attachment added *alongside* the old ones |
| C9 | Edit a nested reply | Same pencil/edit behaviour |
| C10 | Mentions (`@someone`) in an edited comment | Still highlighted after saving |

## D. Permissions

| # | Step | Expect |
|---|---|---|
| D1 | Log in as a different user, open the same comment | No pencil |
| D2 | As a moderator, on someone else's comment | Delete yes, edit **no** (by design — moderators shouldn't rewrite others' words) |
| D3 | Signed out, view a public board | No pencil, no reply form |

Optional, if you want to prove the server (not just the UI) enforces it — as user B,
against user A's comment:

```
curl -i -X PATCH https://<host>/llama_bot/feedback/<fb_id>/comments/<comment_id> \
  -H "X-CSRF-Token: <token>" -b "<session cookie>" \
  -d "feedback_comment[body]=hacked"
```

Expect a redirect with "Not authorized." and the comment unchanged.

## E. Regression watch

- Posting a **new** comment with attachments still works (create path untouched).
- **Paste-to-attach** (Cmd/Ctrl+V into a comment box) still previews correctly — it
  shares the same preview function.
- Reply form still opens/closes.
- Feedback board index cards still show their image previews.

## Known gaps (not bugs)

- The **requests** board (`/llama_bot/requests`) still has no attachments or edit on
  comments — untouched by this change.
- The `(edited)` marker is derived from `created_at` vs `updated_at`, so adding an
  attachment to an old comment also marks it edited. No new DB column was added.
